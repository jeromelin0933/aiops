### 3.2 Current Implemented Runtime Architecture

下圖是SPEC-011 v1.2與SPEC-016 v1.1 documentation closure對齊的current logical architecture。Runtime Worker獨立於EventDetectionRunner，從durable authoritative EventStore intake；它不是detector的一部分，Candidate E也不建立第二套Runtime。

```text
Event Detection / EventDetectionRunner
              │
              ▼
Detector-owned EventStore.write()
              │
              ▼
      durable authoritative Event
              │
              ▼
SPEC-011 Runtime Orchestration Worker (singular Runtime authority)
      ├── SPEC-006 Policy Engine
      ├── SPEC-007 Correlation State
      ├── SPEC-008 Incident Management
      ├── SPEC-009 Lifecycle / Workflow
      ├── SPEC-010 Shadow / Unclassified
      └── SPEC-016 Candidate-E orchestration
            ├── Candidate A / B / C / D public capabilities
            └── SPEC-008 publication reads / authorized mutation
```

`EventDetectionRunner ≠ SPEC-011 Runtime Worker`。Detector先完成Event持久化，Runtime才從authoritative EventStore intake；detector return object不是正式process handoff。Runtime只協調when／order／retry／recovery與cross-domain sequencing，各Domain仍擁有其business semantics及side effects。Engine decides. State remembers. Runtime orchestrates. Domain stores own the side effects.

### 3.4 Recovery、Pending與Runtime execution continuity

Runtime normal intake的implemented readiness boundary為：

```text
STARTING
→ authoritative discovery
→ RECOVERY
→ unresolved Intent reconciliation
→ expired Pending handling
→ retry restoration
→ AUTO_ASSIGN reconstruction / reconciliation
→ RCA publication-first classification / reconciliation
→ RCA initial / retry / follow-up / post-context restoration
→ READY
→ normal Event intake
```

Restart是recovery，不是reset；recovery-relevant authority尚無法可靠讀取或分類時不得開始normal intake。

Active Pending wake-up由SPEC-011週期性排程並提供authoritative timezone-aware Runtime `now`；SPEC-007決定`PENDING_RECHECK`／`PENDING_EXPIRED` phase，SPEC-006依exact policy及latest views reevaluate。Runtime不得自行決定Pending phase或重設absolute expiry。

SPEC-011的independent SQLite Runtime Work Store（D2）只保存orchestration continuity，例如outstanding orchestration step、retry continuity、AUTO_ASSIGN work，以及SPEC-016 RCA root／stage／operation references、Attempt-bound retry consumption、singleton follow-up frontier、absolute wake與publication continuation。它不是Event、Pending、Processed、MutationIntent、Incident、Shadow、Workflow、Evidence、Knowledge、Generation result或RCA Artifact authority，也不取代任何domain store。

RCA startup recovery先以SPEC-008 receipt／relationship與Candidate-A publication facts進行publication reconciliation，再分類validated D result、retryable／non-retryable／repair-required failure、exhausted budget、follow-up／post-context、STALE Current與initial Incident obligations。不可靠讀或矛盾authority對受影響RCA capability Fail Closed；不建立第二套startup loop。

### 3.5 Incident handoff與cross-store consistency

CREATE_NEW的approved高層順序為：

```text
CREATE_NEW
→ durable OPEN Incident
→ correlation Processed
→ separate AUTO_ASSIGN orchestration
→ SPEC-009 AUTO_ASSIGN
→ ASSIGNED
```

AUTO_ASSIGN failure不得rollback已durable的OPEN Incident。Runtime recovery可依authoritative Processed destination、Incident state與workflow evidence重建outstanding AUTO_ASSIGN；完整recovery contract以SPEC-011為準。

Cross-store consistency採domain-local transactions、SPEC-007 MutationIntent、stable operation identity、domain receipts/results與Runtime reconciliation。不使用cross-store 2PC、shared ownership database或cross-store foreign key。Runtime是coordinator，不是所有domain stores的owner。

Retry／clock只在本DDS保留高層邊界：Runtime使用deterministic bounded retry及authoritative timezone-aware Runtime clock；正式schedule、failure disposition與time semantics以SPEC-011為準，避免在supporting document duplicate contract detail。

Runtime亦已實作structured telemetry，涵蓋startup、intake、Pending、domain attempt、retry、reconciliation、AUTO_ASSIGN及stop observability；telemetry只提供operational evidence，不成為domain state、receipt或business audit authority。

### 3.6 Docker Runtime topology

Host與Docker使用相同Runtime core。Compose service名稱為`runtime`，使用`docker/runtime/Dockerfile`及`configs/runtime_orchestration.docker.yaml`的`continuous` loop；host config則使用`run-until-idle`。Docker topology為：

```text
runtime service
├── runtime-events → /app/events
├── runtime-state  → /app/var/runtime_orchestration
└── runtime-knowledge → /app/var/knowledge_index
```

`runtime-events`保存authoritative EventStore；`runtime-state`保存彼此獨立的Correlation State、Incident、Shadow、Runtime-work及RCA A／B／D SQLite files；`runtime-knowledge`保存Candidate-C local Knowledge index artifacts。Named volumes提供restart continuity，不建立shared authority database。Historical SPEC-011 correlation Runtime graceful stop、controlled drain、restart recovery與opt-in Docker E2E已驗證；Candidate-E Docker execution為`NOT EXECUTED`。此single-process／single-node topology沒有HA、distributed coordination、broker、exactly-once transport infrastructure或cross-store 2PC。

Current `rca:` config提供Candidate-A／B／D store paths、Knowledge／Generation／Evidence config references及Loki／Prometheus local endpoints。Provider clients在實際invocation時lazy acquisition；文件中不保存credential。Exact configuration authority與validation以SPEC-011／SPEC-016及committed config implementation為準，本DDS不新增normative schema。
