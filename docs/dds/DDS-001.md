## 3. Architecture、metrics與current Runtime topology

### 3.1 Current implemented metrics deployment

目前 metrics deployment topology：

```text
Metrics Generator
  → host exporter :8000
  → Prometheus container scrape target host.docker.internal:8000
  → Grafana
```

Metrics Generator 提供四個 Gauge：

| Metric |
|---|
| `system_memory_usage_pct` |
| `api_p95_latency_ms` |
| `api_requests_per_sec` |
| `db_pool_active_connections` |

目前 `api_requests_per_sec` 是 single series；四個 Gauge 均未使用 dynamic scenario、service 或 detector labels。這些是 current implementation / deployment reality，不是新的 detector normative contract。

整體產品方向可高階表達為Logs／Metrics → Event Detection → downstream Alert Correlation → Incident → RCA → operational／presentation interfaces。SPEC-006～011已依各自核准scope實作，Host與Docker Runtime E2E已驗證；RCA／RAG、Dashboard、Jira、Discord／ChatOps、Email fallback、Knowledge workflow、automatic remediation與production hardening仍pending。PRD-003 v1.0 Final持續定義correlation／Incident detailed requirements；DDS-001不是該domain的design authority。

### 3.2 Current Implemented Runtime Architecture

下圖是SPEC-011 v1.0已實作的current logical architecture。Runtime Worker獨立於EventDetectionRunner，從durable authoritative EventStore intake；它不是detector的一部分。

```text
Event Detection / EventDetectionRunner
              │
              ▼
Detector-owned EventStore.write()
              │
              ▼
      durable authoritative Event
              │
              ▼
SPEC-011 Runtime Orchestration Worker
      ├── SPEC-006 Policy Engine
      ├── SPEC-007 Correlation State
      ├── SPEC-008 Incident Management
      ├── SPEC-009 Lifecycle / Workflow
      └── SPEC-010 Shadow / Unclassified
```

`EventDetectionRunner ≠ SPEC-011 Runtime Worker`。Detector先完成Event持久化，Runtime才從authoritative EventStore intake；detector return object不是正式process handoff。Runtime只協調when／order／retry／recovery與cross-domain sequencing，各Domain仍擁有其business semantics及side effects。Engine decides. State remembers. Runtime orchestrates. Domain stores own the side effects.

### 3.3 Runtime authority map

| Authority | Responsibility |
|---|---|
| SPEC-006 | Correlation decision、candidate與policy semantics |
| SPEC-007 | Claim、Pending、MutationIntent、Processed、Blocked與phase determination |
| SPEC-008 | Incident create／attach及Event→Incident ownership |
| SPEC-009 | AUTO_ASSIGN、Incident lifecycle與human workflow |
| SPEC-010 | Shadow mutation及Event→Shadow ownership |
| SPEC-011 | Runtime orchestration、sequencing、scheduling、startup recovery與safe retry timing |

Runtime不得以自己的record、telemetry或control flow取代上述domain authority。

### 3.4 Recovery、Pending與Runtime execution continuity

Runtime normal intake的implemented readiness boundary為：

```text
STARTING
→ authoritative discovery
→ RECOVERY
→ unresolved Intent reconciliation
→ expired Pending handling
→ retry restoration
→ AUTO_ASSIGN reconstruction / reconciliation
→ READY
→ normal Event intake
```

Restart是recovery，不是reset；recovery-relevant authority尚無法可靠讀取或分類時不得開始normal intake。

Active Pending wake-up由SPEC-011週期性排程並提供authoritative timezone-aware Runtime `now`；SPEC-007決定`PENDING_RECHECK`／`PENDING_EXPIRED` phase，SPEC-006依exact policy及latest views reevaluate。Runtime不得自行決定Pending phase或重設absolute expiry。

SPEC-011的independent SQLite Runtime Work Store（D2）只保存orchestration continuity，例如outstanding orchestration step、retry continuity、AUTO_ASSIGN outstanding work與restart continuity。它不是Event、Pending、Processed、MutationIntent、Incident、Shadow或Workflow authority，也不取代任何domain store。

### 3.5 Incident handoff與cross-store consistency

CREATE_NEW的approved高層順序為：

```text
CREATE_NEW
→ durable OPEN Incident
→ correlation Processed
→ separate AUTO_ASSIGN orchestration
→ SPEC-009 AUTO_ASSIGN
→ ASSIGNED
```

AUTO_ASSIGN failure不得rollback已durable的OPEN Incident。Runtime recovery可依authoritative Processed destination、Incident state與workflow evidence重建outstanding AUTO_ASSIGN；完整recovery contract以SPEC-011為準。

Cross-store consistency採domain-local transactions、SPEC-007 MutationIntent、stable operation identity、domain receipts/results與Runtime reconciliation。不使用cross-store 2PC、shared ownership database或cross-store foreign key。Runtime是coordinator，不是所有domain stores的owner。

Retry／clock只在本DDS保留高層邊界：Runtime使用deterministic bounded retry及authoritative timezone-aware Runtime clock；正式schedule、failure disposition與time semantics以SPEC-011為準，避免在supporting document duplicate contract detail。

Runtime亦已實作structured telemetry，涵蓋startup、intake、Pending、domain attempt、retry、reconciliation、AUTO_ASSIGN及stop observability；telemetry只提供operational evidence，不成為domain state、receipt或business audit authority。

### 3.6 Docker Runtime topology

Host與Docker使用相同Runtime core。Compose service名稱為`runtime`，使用`docker/runtime/Dockerfile`及`configs/runtime_orchestration.docker.yaml`的`continuous` loop；host config則使用`run-until-idle`。Docker topology為：

```text
runtime service
├── runtime-events → /app/events
└── runtime-state  → /app/var/runtime_orchestration
```

`runtime-events`保存authoritative EventStore；`runtime-state`保存彼此獨立的Correlation State、Incident、Shadow及Runtime-work SQLite files。Named volumes提供restart continuity，不建立shared authority database。Graceful stop、controlled drain、restart recovery與opt-in Docker E2E均已驗證；此single-process／single-node topology沒有HA、distributed coordination、broker、exactly-once transport infrastructure或cross-store 2PC。

## 4. Log path and Promtail / Loki boundary

目前 log pipeline 的 host 與 container path 明確如下：

```text
Host physical log:  logs/aiops.json.log
Compose mount:      ./logs:/var/log/aiops
Promtail reads:     /var/log/aiops/*.log
Loki push endpoint: http://loki:3100/loki/api/v1/push
```

`logs/aiops.json.log` 與 `./logs` 是 host-relative path；`/var/log/aiops/*.log` 是 Promtail container 內的 path。此處僅記錄既有 deployment configuration。
